# Knowledge Context：项目介绍与复盘

> 本文以仓库当前实现和本地验收为依据。以下第一人称表达是项目发起者可以使用的介绍草稿，不意味着其亲手编写了全部代码。实际分工是：人提出场景、产品判断、验收要求与反馈，AI 协助方案细化并承担主要编码、调试与验证执行。

## 1. 60–90 秒项目介绍

我用 AI 辅助开发了一个本地优先的个人知识库，叫 Knowledge Context。最初想解决的是资料越来越多，但真正复盘项目时，仍然要反复翻文件、补背景，还容易把不同阶段的数据和个人贡献混在一起。

所以我把产品拆成两条路径：一条是“问我的资料”，上传文档后基于检索到的原文回答，重要结论可以点开引用核对；另一条是“继续我的项目”，将用户明确确认的事实、偏好和决策保存为长期记忆，减少下次重新介绍背景的成本。

我主要负责明确场景、选择产品方向、提出验收用例和体验反馈，AI 协助技术设计并完成主要编码。开发过程中，我发现“能生成回答”和“能严谨复盘”差别很大：测试中，具体指标查询可以正确命中资料，但完整总结仍可能漏掉“待上线”的限制。因此现阶段我把它定位为可追溯的复盘助手，而不是自动事实审核器。下一步优先补事实状态、版本冲突和部分拒答，再提升检索能力。

## 2. 针对什么场景和用户

### 最先验证的场景

用户有一批项目说明、会议记录、阶段数据和复盘材料，希望回答三个问题：项目为什么做、过程中做了哪些取舍、哪些结论确有证据。回答不仅要顺畅，还要能回到具体资料核对。

第二个场景是持续推进一个个人项目：希望系统记得已确认的表达偏好、约束、决定和当前背景，不必每次重复输入。

### 用户范围

当前以项目发起者本人为种子用户，兼顾资料密集的产品经理、研究者、学生和个人项目开发者。这些是适用人群假设，不是已经验证的客户群或已有用户规模。由于是个人 vibe coding 项目，第一阶段优先跑通真实任务和完整闭环，不先做复杂用户分层、商业化或团队协作。

### 与普通 AI 聊天的区别

核心不是增加一个聊天框，而是管理两种不同的信息：资料负责可追溯的证据，长期记忆负责经确认的个人上下文。资料问答不使用个人记忆和历史模型回答充当证据；聊天里发现的偏好也不未经确认自动成为事实。

## 3. 产品是怎么设计的

1. 先明确价值：从“存很多笔记”收敛为“回答有依据，项目能接着推进”。
2. 拆开两种模式：资料问答强调来源与边界，项目助手强调连续性，避免用户不知道 AI 到底在参考什么。
3. 设计最短操作链：上传或勾选资料 → 提问 → 点击引用核对。首页直接展示文件，增加名称搜索、类型筛选、选择状态和上传入口。
4. 把确认机制放进核心链路：候选记忆可以编辑、确认、合并、替代或拒绝，支持审核撤销和历史版本恢复。
5. 用真实任务验收：不仅检查接口成功，还检查断言有没有出处、更新删除是否生效、团队事实会不会被改写成个人成果。

视觉设计参考用户选择的知识库后台和浅色工作台：浅灰导航、白色内容区、紫色操作强调、紧凑文件列表；原文使用右侧抽屉，长文阅读时保留标题与关闭按钮。设计优先服务上传、选择、提问、核对，而不是堆叠装饰或不可用按钮。

## 4. 技术路径与取舍

| 模块 | 当前实现 | 为什么这样做 / 边界 |
|---|---|---|
| 前后端 | Next.js 16、React 19、TypeScript；服务端路由处理文件与模型调用 | 一套项目打通界面和后端；避免密钥放到浏览器 |
| 模型 | 兼容 Chat Completions 的 Provider，已做 DeepSeek 本地联调；可配置其他兼容服务 | 先复用通用模型，不训练模型；资料问答温度为 0，但这不能保证事实正确 |
| 文件解析 | PDF 使用 pdf-parse；DOCX 使用 mammoth；文本直接读取 | 限单份 10 MB、解析最多 100,000 字符；原件保存，超限标记部分解析；扫描件 OCR 未实现 |
| 资料存储 | Node.js 24 内置 SQLite；原件、解析文本、片段与版本事务保存 | 本机可直接运行，无需额外数据库；不是跨设备云盘 |
| 资料检索 | 中文二元词/英文词匹配；最多选择 20 份文档，每次召回最多 12 个约 1,200 字符片段 | 实现成本低、可解释；语义召回、跨文档覆盖和状态限制识别仍有限 |
| 引用约束 | 证据编号由服务端生成，校验模型返回引用；回答前后检查资料是否仍为当前版本 | 防止引用不存在或引用已更新资料；尚未逐句验证“原文是否充分支持结论” |
| 长期记忆 | 事件、候选、有效记忆、记忆版本、审核记录、上下文快照；默认 SQLite，可选 PostgreSQL | 确认后生效且可恢复；PostgreSQL 集成未在本次环境执行验证，pgvector 检索属于后续方向 |
| 上下文组装 | 按范围、相关性、重要性、时效及估算 token 预算选择有效记忆 | 控制上下文规模并记录选择原因；当前是规则评分，不是完整学习式记忆系统 |
| 对话可靠性 | 先保存问题，再保存答案；请求标识去重、未完成状态与刷新恢复 | 降低网络中断造成的记录丢失；不宣称覆盖所有故障情形 |
| 验证 | TypeScript、Vitest、生产构建、独立测试库及浏览器操作 | 单元测试和真实问答分层验证；通过构建不等于问答语义全部正确 |

资料路径：文件解析、分片与保存 → 检索相关原文 → 模型生成带引用回答 → 校验引用和版本状态 → 保存并展示。

记忆路径：用户输入 → 提取候选 → 用户审核 → 写入有效记忆与版本 → 下次按需组装上下文。

目前更准确的称呼是“带受控记忆和检索增强问答的助手”。系统尚未具备自主规划、工具执行、结果校验和重试闭环，不应包装为已实现的多 Agent 系统。

## 5. 难点、处理方式与仍未解决的部分

| 难点 | 已做处理 | 当前边界 |
|---|---|---|
| 资料和个人事实混淆，可能污染长期记忆 | 两条模式隔离；文档问答不自动提取个人记忆，个人候选确认后才生效 | 规则提取仍可能把问句当偏好，或丢掉跨句限定，人工确认不能替代识别改进 |
| 模型回答流畅，但事实可能不可靠 | 仅向资料模式提供检索证据，要求引用，缺依据时拒答；原文可点击核对 | 引用有效不等于结论正确；复合问题还可能整题拒答 |
| 新旧文档和删除后的证据不一致 | 保存文档版本；逻辑删除后退出检索；生成结束检查证据是否被更新或删除 | 独立上传的 v0.1/v0.2 文件不会自动识别为同一文档；历史回答不会自动抹除 |
| 问答刷新或中断后丢失 | 问题先落库、答案后落库，保存生成状态和服务端历史 | 草稿未保存；无完整后台任务系统和大规模并发验证 |
| 页面看起来有功能，但用户找不到操作 | 增加清晰用途入口、显式上传、资料列表与范围提示、固定输入区和原文抽屉 | 当前是本地响应式版本，没有正式可用性研究或留存数据 |
| 批量选择 11 份资料只处理前 5 份 | 最新界面明确检查每轮剩余数量，超过时提示本次未上传，要求重新选择 | 尚未实现不受每轮 5 份限制的后台上传队列 |
| 文档内部存在“已采取动作”和“仍待上线”的矛盾 | 真实文件测试发现并记录，核对最终稿时保留待确认状态 | 自动检测尚未完成，不能声称已解决；需增加状态事实抽取和冲突回归测试 |

安全上，早期 V1 的前端密钥暴露已从当前工作文件中移除，V2 只在服务端读取密钥，并排除本地数据库和环境配置。但 Git 历史或旧部署中已出现过的凭证仍需吊销；删除当前文件中的字符串不等于撤销凭证。当前没有登录授权、完整脱敏和安全运营能力，不应直接作为公开多人服务。

## 6. 我是怎么和 AI 协作的

这不是“给 AI 一句话，然后接受整套代码”，而是把 AI 纳入可验收的开发循环。

### 人承担的部分

- 提出真实场景，明确产品不是单纯存笔记，而是基于自己的资料和上下文回答。
- 对“系统持续记住已确认事实、偏好和决策”作产品取舍。
- 提出 18 类验收场景，包括无答案、更新、删除、引用、权限和注入等；提供真实资料供指定范围测试。
- 从操作体验发现问题：没有输入/上传入口、记忆类型选项过多、不理解产品用途；选择 UI 参考并审核方向。
- 决定哪些记忆可以确认，哪些事实需要补充，哪些输出能作为最终材料。

### AI 承担的部分

- 把需求拆成架构、数据模型、页面与接口，提出实现顺序和技术取舍。
- 编写主要代码、数据库及测试，处理构建、解析和本地运行问题。
- 执行浏览器与接口验证，记录真实结果，并将失败案例反馈为产品改进项。
- 整理文档与复盘草稿；不能代替用户证明个人经历或确认来源未支持的事实。

### 复盘后可以改进的协作方式

1. **先写验收，再扩功能。** 先准备“事实正确/应拒答/需追问/版本冲突/个人归因”样例及预期，再让 AI 实现，避免完成感只来自页面和代码量。
2. **把完成度拆开。** 功能接通、异常可恢复、语义正确、体验可用、安全边界是不同门槛；不能因为 38 个单测通过就宣称模型准确。
3. **缩短迭代颗粒度。** 每次只做一个可验证链路，形成小提交与回归记录。不要一直在本地堆积未提交修改，到发布时才整理。
4. **让 AI 说明证据。** 完成报告必须写清测试环境、数据范围、执行结果、未覆盖项和已知失败；没有运行的测试不能写成通过。
5. **控制数据和权限。** 公共测试用合成数据；真实资料只在明确范围内处理；模型密钥只放服务端，不上传到仓库。
6. **人保留判断权。** AI 可以推荐类型、发现冲突、生成总结，但确认长期记忆、个人成果归因和发布范围仍由人决定。

## 7. 当前能证明什么，不能证明什么

- 发布前可重复的工程检查：类型检查与生产构建；现有测试 38 项通过，1 项 PostgreSQL 集成测试因未配置专用数据库而跳过。
- 一轮指定真实资料测试：11 份文档、约 7.65 万字符、7 次真实问答；文件副本与原件一致。它证明任务可执行，并暴露综合总结与状态边界问题，不是线上用户规模或模型准确率。
- 原始问答和私人资料保留在本机忽略目录，不随源码发布；公共仓库仅保留脱敏的能力与问题说明。
- 没有经过正式评估的节省时间、留存、付费转化或 ROI 数据；不编造“效率提升 X%”。
- 当前目标是把“有出处的草稿”推进为“边界明确、容易核对的复盘助手”，还不是零幻觉知识库、完整自主 Agent 或企业级 SaaS。

## 8. 下一阶段优先级

**P0：事实与状态。** 为数字保留日期、样本、分母、来源和实施状态；识别同文档/跨版本冲突；把回答拆成有依据部分、待确认部分和需要补充的材料。

**P1：检索与记忆质量。** 建立固定问答回归集，再根据漏召回证据引入关键词与向量混合检索、重排、邻近片段扩展和主题覆盖；记忆提取先区分陈述、提问、否定、假设和引用。

**P1：可用性。** 完善上传队列、Markdown/表格展示、对话搜索导出、错误反馈记录和版本关系提示。

**扩大使用前：权限与隐私。** 增加身份认证、资源授权、日志最小化、敏感信息策略和备份恢复；不能只凭 projectId 筛选就宣称多用户隔离。

## 9. 可以诚实使用的一句话

“这是一个由我定义场景、设计验收并持续迭代，借助 AI 完成主要开发的个人知识库项目；我重点解决的是资料证据、个人记忆和用户确认之间的产品边界，而不是把通用模型包装成已经可靠的全自动 Agent。”
